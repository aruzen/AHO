## 再実装優先

### クリック取得 / ピッキング経路の再設計

対象:

- `AHO/Main.cpp`
- `AHOLi/AHO/src/io/mouse.cpp`
- `AHOLi/AHO/src/io/input_manager.cpp`
- `AHOLi/AHO/include/AHO/object/object.hpp`
- `AHOLi/AHO/include/AHO/resource/object_hitbox.hpp`
- `VSLi/VSL/src/vulkan/render_pass.cpp`
- `VSLi/VSL/include/VSL/vulkan/render_pass.hpp`
- `VSLi/VSL/src/vulkan/commands/render_pass_begin.cpp`
- `VSLi/VSL/src/vulkan/stages/id_picking.cpp`

状態:

- クリック入力、カーソル座標、ID picking render pass、ID buffer read、オブジェクト解決が一つの抽象として接続されていない。
- `AHO/Main.cpp` では `mouse->leftClick()->up()` の直後に `picking_render_pass.read(command_manager, in_flight, 500, 500)` を直接呼んでおり、クリック位置ではなく固定座標を読んでいる。
- `IDPickingRenderPass::read()` は render pass の責務を越えて、barrier、staging buffer、command phase、fence wait、CPU readback まで抱えている。
- `IDPickingRenderPass` は swapchain image 数に合わせた picking buffer を自前で持つが、通常描画 render pass / picking render pass / frame buffer / resize recreate の関係が明示的なシステムとしてまとまっていない。
- `RenderPass` と `IDPickingRenderPass` が継承/別クラスで増える形になっており、picking 用 attachment や readback 対象を増やしたい場合に class を増殖させる設計になりやすい。
- RenderPass の attachment、subpass、dependency、clear value、framebuffer 構成が分散しており、ID picking、depth picking、normal picking、stencil/object mask などを横展開しづらい。
- GPU readback が `IDPickingRenderPass::read()` に直結しており、他の readback 用途へ再利用できる staging/readback 抽象がない。
- `IDPickingRenderPassBegin` は color attachment と picking attachment の clear value を手書きしており、attachment 定義と begin command の対応が型や definition で保証されない。
- `pipeline_layout::IDPicking` は color blend attachment を `std::any` pool 経由で追加しており、他の color blend 設定との合成順序に依存する。
- `object.hpp` と `object_hitbox.hpp` は空で、クリックされた ID を AHO の object / hitbox / scene selection に戻す受け皿がない。
- Mouse/InputManager は GLFW の raw handle を `void*` として保持しており、クリックイベントと座標系変換、framebuffer scale、viewport/scissor の関係を扱わない。

影響:

- クリック取得のための特別扱いが AHO アプリ、VSL render pass、pipeline stage、command、input に分散している。
- 「クリックされたもの」を取得したいだけの利用者が、picking 用 render pass、frame buffer、shader、ID buffer readback、座標指定をすべて意識する必要がある。
- DPI scaling、window resize、viewport/scissor 変更、swapchain image index と frame index のずれで誤った pixel / image を読む可能性がある。
- object ID の割り当て、0 を未選択にする規約、ID の寿命、削除済み object の扱いが未定義。
- GPU readback がクリックイベントの処理に直結しており、同期コストや frame 遅延を隠蔽できない。
- ID picking 以外の picking buffer を増やすたびに RenderPass / FrameBuffer / BeginCommand / readback の組を特別扱いで追加することになる。
- RenderPass の設計が固定化されているため、通常描画に追加 attachment を挿す、picking 専用 pass を作る、既存 pass の subpass に picking を追加する、という選択を API として比較できない。

次の作業:

- AHO 側に `Pickable` / `Clickable` / `HitTarget` / `ScenePicker` 相当の責務を設け、VSL の ID picking を直接アプリから触らない構成にする。
- input は「button state」と「cursor position」を同じ frame snapshot として取得できる API に寄せる。
- window cursor 座標、framebuffer 座標、viewport/scissor 座標、picking image 座標の変換を一箇所に集約する。
- RenderPass は `RenderPassDefinition` / `AttachmentDefinition` / `SubpassDefinition` / `ClearValue` のようなデータ定義から作る。
- ID picking は `IDPickingRenderPass` 固有実装ではなく、`AttachmentRole::ObjectId` のような attachment role と、そこへ出力する pipeline stage / shader contract として表現する。
- GPU readback は render pass から分離し、`ReadbackBuffer` / `PixelReadbackRequest` / `FrameReadbackQueue` 相当の汎用 API にする。
- ID buffer は render pass ではなく picking system / frame resource / attachment resource が所有し、resize と swapchain recreate に追従させる。
- `read(x, y)` は即時 fence wait ではなく、可能なら frame 遅延つき request/result API にする。同期が必要な debug API は別名で明示する。
- ID picking を増やす場合は class 追加ではなく、attachment role と readback format を追加するだけで済む形にする。
- object ID の発行、未選択 ID、削除済み ID、複数 viewport の規約を AHO 側で定義する。
- 最小実装として、`mouse->cursor()->state()` から framebuffer pixel を計算し、固定値 `500, 500` を排除する。

### Vulkan frame/present 処理の image index 扱い

対象:

- `VSLi/VSL/src/vulkan/phase.cpp`

状態:

- `acquireNextImageKHR()` の result check は追加済み。
- ただし `DefaultPhase::submit()` で acquire した `imageIndex` ではなく `manager.getCurrentBufferIdx()` を present に渡している。

次の作業:

## まとめ

最初に手を付けるべきなのは次の 4 点。

1. `AHO/resource/buffer.hpp` の未定義動作を解消する。
2. クリック取得 / ID picking / object selection を AHO 側のまとまった API として再設計する。
3. `phase.cpp` の present index と swapchain recreate 処理を直す。
4. 型安全 pipeline の範囲を決め、`TypedVertexInput::injection()` と Push Constant 検証を実装する。

この順に進めると、実行時クラッシュにつながる箇所を先に減らし、その後に AHO 側の設計上の価値である型安全 pipeline を固められる。
